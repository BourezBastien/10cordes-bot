# Plan — 10cordes-bot : docs consolidées + fondations P0 (étapes 1–5)

## Contexte

Le bot doit devenir un **all-in-one modulaire digne de MEE6/Koya/Crow** : chaque fonctionnalité = module activable/désactivable en live, avec **dépendances obligatoires entre modules** (ex: `shop` → `economy`), **langue par utilisateur** (pas par serveur), **slash commands uniquement**, et un **registry d'outils façon MCP** utilisable en **chat ET en vocal**. L'analyse des 200+ suggestions validées de la communauté Crow Bots fournit le backlog priorisé (dédupliqué). Session validée par l'utilisateur : **consolidation des docs + fondations P0 étapes 1–5** (le code API/auth/dashboard/vocal vient ensuite).

## Décisions d'architecture (veille validée)

1. **Slash only** — le pipeline prefix du framework n'est pas utilisé.
2. **Modules & sous-modules avec graphe de dépendances** — le catalogue (`module.catalog.ts`) gagne `dependsOn: string[]` (obligatoire) et `recommends?: string[]` (suggestion à l'activation, ex: levels → role-rewards). Règles :
   - **Enable** d'un module → auto-enable de ses dépendances (avec confirmation éphémère listant ce qui a été activé).
   - **Disable** → calcul du graphe inverse : les modules dépendants activés **seraient désactivés**, sauf ceux **également requis par un autre module restant actif**. Le message liste précisément la cascade avant confirmation (boutons Confirmer/Annuler via `@spraxium/components`).
   - Un module dont une dépendance est désactivée → ses commandes sont bloquées par le guard avec message explicite (`ModuleDependencyException`).
3. **Langue par utilisateur, jamais par serveur** — résolution : préférence user (`/language set`) > langue du client Discord (`interaction.locale`, capturée à la première interaction) > défaut du bot. Le framework (`I18nService.tUser`) supporte déjà la résolution user-first ; store i18n persisté en Prisma via `I18nStore`. Dashboard : préférence dans le profil better-auth, UI traduite i18next.
4. **ToolRegistry (MCP interne)** — chaque module expose des **tools** typés (nom, description, Zod params, handler, `requiredModules`). Registry unique consommé par 3 frontends : **assistant chat** (mention/canal dédié/DM), **assistant vocal** (STT → tool), **serveur MCP over HTTP** (P3, via `@spraxium/http`). Exécution : hooks déterministes (patterns de phrases fr/en) d'abord, **LLM tool-calling** (AI SDK + OpenRouter) en fallback avec budget/guild. Tools filtrés selon les modules activés du serveur (cohérence avec le graphe de dépendances).
5. **Assistant vocal (P2)** — `@discordjs/voice` + **Silero VAD** (ONNX, supérieur au WebRTC VAD) + STT (**Deepgram streaming** ou Whisper API, Opus→PCM via prism-media/ffmpeg) + TTS réponse. Opt-in par serveur, budget strict.
6. **Partage d'écran par bot : VERDICT NON** — l'API officielle des bots ne supporte que l'audio (`@discordjs/voice`) ; le Go Live est client-only. Les contournements (self-bots type Discord-video-stream) **violent les ToS Discord → refusé**. Documenté dans la roadmap comme limite plateforme.
7. **Auth dashboard : better-auth confirmé** — Lucia est déprécié (mars 2025) et son auteur recommande better-auth ; Discord-only = pattern standard (email/password désactivé). Cookie sessions, adapter Prisma, tables générées dans notre schema. Le dashboard affiche : guilds où le bot est + droits de l'user (ManageGuild) + guilds où l'user peut inviter (bouton **Setup** = URL OAuth scope `bot` + permissions).
8. **Économie/musique restent P3/P4** (validé) ; musique = future app séparée du monorepo.

## Livrable 2 — P0 étapes 1–5 (implémentation)

**P0-1 Monorepo** — `git mv` du bot vers `apps/bot`, création `packages/shared`, `pnpm-workspace.yaml` (apps/*, packages/*), Biome racine + `biome.json`, vitest, scripts racine (`-r typecheck/test`). Mise à jour `AGENTS.md` (nouveaux chemins).

**P0-2 Prisma + SQLite** — `apps/bot/prisma/schema.prisma` : `Guild {id, settings Json}` , `GuildModuleState {guildId, moduleId, enabled, whitelist Json}` (unique guildId+moduleId), `UserLocale {userId, locale}` (+ tables better-auth documentées en commentaire, générées à l'étape 6). `migrate dev`.

**P0-3 packages/shared (Zod)** — `src/schemas/guild-config.ts` (langues, salons, welcome, cooldowns, quotas, whitelists, messages d'erreur custom, template options), `module-whitelist.ts` (channels/roles/users), `module-catalog.ts` (types `ModuleDescriptor` avec `dependsOn`/`recommends`/`group`), `api-dto.ts`, `errors.ts` (codes). Types inférés `z.infer` consommés par bot (+dashboard plus tard). Tests vitest ≥ 80 %.

**P0-4 Services fondamentaux** — `GuildConfigService` (cache Map + patch Zod + defaults + export/import JSON pour config transfer) ; `/config view|set|export|import` (autocomplète sur clés du schéma) ; **`TemplateEngine`** (`render(template, context)` + variables/register) ; **`LocaleService`** (get/set per-user, auto-capture `interaction.locale` via listener `interactionCreate`, intégrée à l'i18n store Prisma) ; `/language set`.

**P0-5 ModuleManager étendu** — catalogue avec dépendances ; `ModuleManagerService` : `enableWithDependencies`, `disableWithCascade` (graphe inverse + protection « utilisé par un autre module actif ») ; `/modules configure <module>` (whitelists salons/rôles/users, cooldown, quota par rôle) ; guard global étendu (ordre : inconnu → global off → guild off → dépendance inactive → whitelist salon → rôle requis → quota/cooldown) ; exceptions dédiées (`ModuleDependencyException`, `ModuleChannelException`) + layouts.
