# AGENTS.md

## Project

**10cordes-bot** - agentic all-in-one Discord bot, **zero commands, 100% conversation-driven** (mention, bot name, or dedicated AI channel). Built on the **Spraxium** framework (`@spraxium/*` v0.9.x, wraps discord.js v14). pnpm monorepo, ESM, Node 22/24/26, Prisma 7 + SQLite, Zod everywhere, **Components V2 as the default rendering** (no "v2" suffixes in names - it is the base UI, helpers live in `apps/bot/src/shared/ui`).

## Monorepo

```
apps/bot          Spraxium bot (+ REST API, better-auth, and the compiled dashboard when DASHBOARD_DIST_DIR is set)
apps/dashboard    Web dashboard (React 19 + Vite 8 + TanStack Router/Query + Tailwind 4, FR/EN)
packages/shared   @10cordes/shared - Zod schemas, BotTool<T>, SkillBlueprint types
docs/             ROADMAP.md (backlog) · ARCHITECTURE.md (deep dive) · audit/
```

Dependency rule: `apps/bot → @10cordes/shared ← apps/dashboard`. Nothing hardcoded: config = Zod schemas in shared; strings flagged for i18n; durations via `parseDurationMs`.

```bash
pnpm --filter 10cordes-dashboard dev      # Vite on :5173, /api proxied to the bot (API_PROXY_TARGET, default http://127.0.0.1:3000)

node apps/bot/scripts/diagnose.mjs [days]            # JSONL log forensics
```

DB migrations: `prisma`, `@prisma/client` and `@prisma/adapter-libsql` are pinned to the same exact version (7.10.1); on the dev DB migrations are applied by hand, never with a reset (see "Data and LLM").

`pnpm arch:audit` has no baseline and no ratchet: zero violation, enforced locally by `pnpm verify` and on every push by CI. Never weaken a rule or add an exception to pass it: fix the code.

CI (`.github/workflows/ci.yml`) has three jobs. `quality` (the only one the branch protection of `main` and `develop` requires) runs `verify`. `secrets` scans the WHOLE git history with gitleaks 8.30.1 (binary downloaded from the official release, pinned, SHA-256 checked, `--redact`: a detected value never reaches a log, only its rule, file, commit and fingerprint). `dependencies` runs on Dependabot pull requests only (on the author of the pull request: after a member updates its branch, the actor of the event is no longer Dependabot) and fails if `pnpm-workspace.yaml` is part of the diff: that file is the supply-chain policy (`allowBuilds`, release age exceptions), never written by an automatic update. Dependabot (`.github/dependabot.yml`) runs weekly on npm and GitHub Actions and groups minor and patch updates; it does not set `target-branch`, because `develop` is the default branch and setting it would remove these options from security updates. **A green Dependabot pull request is not an upgrade**: on 2026-11-25 the pull requests for `@spraxium/components@1.0.2` and `@spraxium/i18n@2.0.2` were green and were regressions (the framework renumbered to 0.9.x on 2026-11-09, after publishing its 1.x and 2.x). Before merging a dependency update, read its publication date and its declared dependencies on the npm registry (the `time` and `versions` fields of `https://registry.npmjs.org/<package>`), and start the bot.

## Architecture

- `apps/bot/src/main.ts` - only file touching `SpraxiumFactory`: validate env → create → `useModule(AppModule)` → `provide(AppEnv)` → `listen()` → purge Discord slash-command registry at boot.
- `apps/bot/src/app.module.ts` - root module; every feature module must be in `imports`. Infra modules (memory, records, rules, integrations, guild-config, providers, action-plan, assistant) are `@Global`.
- `apps/bot/src/app.env.ts` - `@EnvSchema()` extending `SpraxiumBaseEnv`. Generic `LLM_API_URL/KEY/MODEL/EFFORT` (no vendor prefixes), plus the optional `KIE_API_KEY`, `KIE_MODEL`, `PIXELLAB_API_KEY`: read only to fill an empty database (see "Instance config lives in the database"). `DISCORD_TOKEN` is the only required var. `SHUTDOWN_GRACE_MS` (milliseconds, 20 s by default, 5 min at most) bounds the drain at shutdown.

### Conversation pipeline (the product)

Message → gate (ignore bots/webhooks unless the test allowlist; `GuildRule.blockedChannelIds` = total silence; free zones vs strict mention elsewhere; social noise ignored without an LLM call) → queue (FIFO per user, 5 parallel with Redis, one at a time without) → `AgentLoop` (max 12 iterations + synthesis fallback) → `ToolRegistryService.run` → `ReplyDelivery` (the final answer, sent once, addressed to the request) → audit + FileLog JSONL.

**Silence while working.** Nothing is published between the acceptance of a request and its final answer: no `[THINKING]` / `[TOOL]` / `[SOURCES]` line, no draft, no step (the `announceStep` tool no longer exists). The only visible trace is the typing indicator (`TypingIndicator`: `sendTyping` every 8 s, held from acceptance, queue wait included, by the queue and by the worker, released in a `finally`). `ReplySession` holds the requested silence and has no access to the channel. `ctx.progress` goes to the JSONL log only (a tool never posts its own progress). Published: the final answer, attachments, surfaces, confirmation plans, and the notices for a redirection, the antispam and an error.

`ToolRegistryService.run` gates, in order: required modules active → RBAC node `deny` → Discord permissions (unless node `allow`) → Zod validation → **approval of any action that modifies, when the guild rule « Confirmer les actions (hors lecture) » is on** → handler → audit. A failed tool becomes an explicit `{ ok: false, summary }` that the model relays; it never throws into the loop.

Tool routing (Anthropic pattern): a core set is always visible (`TOOL_CORE_NAMES` in `tool-selection.ts`: reads, `search_tools`, `search_skills` and the surface and trigger primitives, 19 tools), up to 24 relevant tools hors noyau (`selectRelevantTools`), and `search_tools` expands it on demand. Relevance is scored by `packages/shared/src/tools/tool-search.ts` (name, `keywords`, description, category): give a tool `keywords` in plain words when its name and description do not carry them. The primitives are pinned because a primitive left behind `search_tools` was searched 8 times in a row and never called; the `systemPrompt` of pinned tools is injected in `<TOOLSET>` from turn 1, and `search_tools` only announces tools the caller can run (active modules and permissions).

### Action plans (`modules/action-plan/`, transposed from discord-agent)

When the guild rule `confirmDestructiveActions` (« Confirmer les actions (hors lecture) », OFF by default) is on, the model cannot execute a tool that modifies. The gate (`tool-registry.confirm.ts`) puts the action in wait, the end of the request turns everything waiting for a requester into ONE plan, and the click executes.

- **What waits**: every tool classified `write` in `TOOL_EFFECTS` (`packages/shared/src/tools/tool-effects.ts`), the single source of truth. `read` (lists, gets, searches, exports) and `direct` (tool and recipe search, config thread panels, files and media delivered in reply, translation) never wait. A name missing from the table counts as `write` (the gate closes, it never opens), and `register` refuses a `destructive` tool that the table does not call `write`. A new tool is a compile error until it has its line.
- **Whom the rule binds**: what the model proposes in conversation, nothing else. A context carrying `approvedBy` (a member's click on a surface and a system task, `shared/actions/run-tool.ts`; an approved plan) is already authorized, and so is anything it triggers with that context. Automations created before the rule was turned on keep running.
- `ActionPlanService`: `stage` (in memory, per guild, requester and channel, 10 actions max) → `flush` (review, summary, one plan, one panel, audit `plan.posted`) → `apply` / `cancel` (click). `flush` runs at the end of a request on the Discord channel and on the web channel.
- **Review before display** (`action-plan.review.ts`): each action passes `ActionPlanPolicy.review` on the requester reloaded with `force: true` BEFORE the panel is shown. One the requester cannot execute is left out, and the panel says why (audit `plan.posted`, field `dropped`). When none survives there is no plan: a notice « Rien à confirmer » and an audit `plan.rejected`. An unresolved requester (the rig's webhook) skips the review, which then happens at the click.
- **Summary** (`action-plan.summary.ts`): at `flush`, `PlanSummaryWriter` asks the model for one or two sentences (12 s budget, else the panel shows without). It is display only and never drives execution. `cleanPlanSummary` strips mentions, links, code and markup, and caps it at 600 characters.
- The panel is posted once and never edited while pending. A modified approval message cancels the plan (same rule as discord-agent). Its text stays under Discord's 4 000 characters (`PLAN_LIMITS.textMax`, measured by `shared/ui/v2-text-length.ts`): by fill levels it shortens the summary, then drops it, then counts the actions set aside instead of listing them, then shortens the parameters. Never the list of actions.
- `apply` takes the plan once (`ActionPlanStore.lock`: the status is the row `kind`, so a second click finds it taken), then for each action, in order: `ActionPlanPolicy.review` on the member reloaded with `force: true`, then `registry.run(tool, input, ctx, { approvedBy })`. A refusal or a failure stops the plan with an honest count. A server snapshot is archived before the whole plan.
- `approvedBy` is passed by the server only. The model cannot produce it, and it never re-runs an approved action itself.
- The gate is closed by default: unreadable guild rules block the action (it used to open the gate).
- Policies live in `src/core/security/`: `ActionPlanPolicy` (tool permissions in the guild and in the target channel, member and role hierarchy, snowflake ids on Discord id keys only: `surfaceId`, `skillId` or `recordId` are the application's own), `MemberPermissionPolicy.hasIn / canActOn / canManageRole / grantsOnly`, `ChannelVisibilityPolicy` (`getChannels` returns only what the requester can see).

### POO layer (audited by `arch-audit`, strict)

- **Policy** (`src/core/security/`): the ONLY place Discord permissions, role membership and role hierarchy are read or compared. `GuildAdminPolicy` and `GuildManagerPolicy` (`access-policy.ts`, on a `GuildAccessContext`), `MemberPermissionPolicy` (a `GuildMember`: guild and channel permissions, hierarchy of member and role targets), `PermissionNamesPolicy` (a list of permission names, i.e. `ToolRunContext.permissions` in jobs, triggers and the web channel), `BotPermissionPolicy` (the bot itself), `ChannelVisibilityPolicy`, `ActionPlanPolicy`, `MassMentionPolicy` (a mass ping is for the owner and the Administrators; a system or absent actor never gets one), `AdminOpPolicy`, `CollectionQuotaPolicy`. Elsewhere, build a context with `guildAccessContext`, `accessContextFromNames` or `interactionAccessContext`, and list names with `permissionsOf(member)`. The audit rejects any other read: `PermissionFlagsBits.`, `.permissions.toArray()`, `.permissions.has(`, `memberPermissions`, `.permissions.includes(`, `guild.ownerId ===`, `member.roles.cache.has(...)`.
- **Presenter** (`modules/*/presenters/`): pure classes, data in → complete Discord payload out (flag `IsComponentsV2` included). No API calls, no side effects.
- **Handler** (`modules/*/handlers/`): policy guard → error message → service delegation. Handlers MUST carry the `@spraxium/components` decorators.
- **No file over 300 lines** (rule `GOD_CLASS`), in the bot and in `packages/shared`. Agent tools live in `*.tools.ts` factories (`buildXTools(deps)`, see `records.tools.ts`, `surface.tools.ts`), pure logic in its own module, and a stateful collaborator is a class constructed in the DI service's constructor with explicit dependencies (a class field, never a constructor default). A service stays an orchestrator.
- Runtime accessors (`getLlm`, `getGuildRules`, `getIntegrations`, `getSurfaceRuntime`, `getToolRegistry`, `bindRegistryRuntimeDeps`) break DI cycles. They are bound in a **provider's** `onBoot`.

### Generic interaction engine (`modules/surface/`)

All business UIs (tickets, polls, giveaways, verification, temp voice...) are built ON DEMAND by the agent from primitives, never hard-coded:

- `InteractiveSurface` - persistent layout + state (DB-backed, survives restarts); editable by `surfaceId` OR `messageId`
- `InteractionBinding` - per-button access policy + action pipeline
- `ScheduledTrigger` - BullMQ-backed timers with guaranteed catchup after reboot
- `EventTrigger` - reactions, voice joins, member updates (10 event types)
- Error messages from surface tools are actionable: offending Zod path, valid binding keys, the identifier that was looked up (`surface.errors.ts`)
- **Pipeline references** (`packages/shared/src/schemas/surface-pipeline-refs.ts`): `validateSurfaceDefinition` and `trigger.schedule` refuse `{{steps.N.data.…}}` (a step exposes `value` and `text`, never `data`) and any reference to a step that does not exist yet at that position, nested pipelines included (`{{steps.3.x}}` written in step 1 is refused). Surfaces stored before this rule are not re-validated.

### Multi-provider engine (`modules/providers/`)

Each guild connects providers and binds each capability to one of their models. No vendor is hard-coded:

- Tables `GuildProvider` (slug, protocol, baseUrl, auth type, key encrypted with AES-256-GCM, options, cached catalog) and `CapabilityRoute` (one per guild capability: `chat.default`, `chat.reasoning`, `chat.ingestion`, `image.generate`, `image.edit`, `music.generate`, `tts.speak`, `video.generate`, `web.search`, any `custom.*`; model, optional fallback provider and model, params).
- **Adapters** (one stateless class per protocol, registered in `ProviderAdapterRegistry` by `ProvidersBoot`): `OpenAiCompatibleAdapter`, `AnthropicMessagesAdapter`, `KieUnifiedAdapter`, `GenericHttpAdapter` (templated REST operations described in the provider options). Contract in `AbstractProviderAdapter`: `testConnection`, `discoverModels`, `execute`, `chat`. A key never leaves an adapter (results, errors and logs are redacted).
- **`CapabilityRouterService`**: resolves the active route of a capability, lists the attempts (`attemptsOf`), runs a capability with an automatic fallback (`runCapability`), hands out the credentials of a capability outside conversation (`credentialsFor`).
- **`LlmService` is an orchestrator** (assistant module): `planRequest` decides ONCE per request whether it reasons (`preferReasoning`) and its effort; each turn goes to the route's provider and model (`ChatEndpointPlanner`), with the same route on every turn of the loop. `ChatTransport` serves the SSE-capable protocols itself and bridges the others to their adapter.
- **Fallback rule** (`isFallbackWorthy`): rate limit (429), server error (5xx), network failure, timeout, and only before any text was published. A refused key or an exhausted quota never falls back: the administrator must fix it.
- **Cooldown per model** (`providers/model-cooldown.policy.ts`, pure; `model-cooldown.store.ts`, in memory behind the async `ModelCooldownStore`, so Redis can take it over): after a failure the model that failed is set aside, and the router no longer calls it. The key is guild, provider and model: two guilds sharing an instance copy do not share a rate limit. Causes: 429 (`rate_limited`, reroute), 402 / `quota` (`no_credits`, never reroute), timeout / 408 (`network_error`, reroute), 5xx (`server_error`, reroute). The duration is the one the provider announces (`Retry-After`, rate-limit reset headers: seconds, HTTP date, timestamp or `1m26.4s`), capped at 15 minutes, else a default (60 s, 5 min, 15 s, 30 s). A refused key or another 4xx sets nothing aside: every request must keep saying it. A cooled model is never called: `attemptsOf` orders the attempts so that a model cooled by a reroute-eligible failure comes last, and a cooled attempt resolves with the error of the call that cooled it (the request goes on to the next attempt, or fails at once when the failure may not reroute). A longer cooldown in progress is never shortened. A successful connection check or a provider change clears that provider's cooldowns. It is all lost at restart.
- **Instance config lives in the database** (table `IntegrationConfig`, one row per catalog entry `llm` / `pixellab` / `kie`, key encrypted AES-256-GCM). The environment (`LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL`, `KIE_API_KEY`, `KIE_MODEL`, `PIXELLAB_API_KEY`) only fills a MISSING row, once per process, and the first read of an integration awaits it (`IntegrationService.importFromEnv`, audit `instance.imported`). A row that exists is never rewritten, and once the database knows any integration the environment is ignored for the whole catalogue. The keys can then be commented out of the `.env`; `ENCRYPTION_SECRET` or `BETTER_AUTH_SECRET` must stay (it derives the master key). `LlmService` reads the instance through `IntegrationService` only: no other `LLM_*` fallback anywhere.
- **Instance defaults, ONE table** (`providers/instance-defaults.ts`, pure plan in `instance-defaults.plan.ts`): the AI providers copied into each guild (the provider of the instance host, such as `deepseek-official`; `kie-ai`) and the routes that go with them. Model ids come from the adapter catalog (`KIE_MODEL_CATALOG`), never hard-coded: `image.generate` and `image.edit` on the image model, `music.generate` on the music one. A family the catalog does not declare (`tts.speak`, `video.generate`) stays unbound and is reported; `web.search` is unbound (no protocol serves it). Three paths share the plan: the first resolved request of a guild (`ensureMigrated`, audit `provider.legacy_migrated`), boot and any change of the instance (`reconcileInstance`, audit `provider.defaults_applied` only when something moved). Copies carry a `_source` marker and follow the instance (key rotated, model changed). A provider or a route created by an administrator is never touched; on a copy, a route whose model the administrator changed keeps it; the slug of an administrator's provider is never taken (suffix `-instance`). PixelLab is not a provider any more: its old copies are removed.
- **Linked conversation routes** (`provider-route.links.ts`): `chat.reasoning` and `chat.ingestion` follow a change of `chat.default` as long as they shared its exact target (provider, model, no fallback, same params). Reason: the intent heuristic sends most real sentences to `chat.reasoning`, so rebinding the default alone would look ineffective. Once an administrator binds one of them separately, it is independent. `bindRoute` returns `{ followedBy }`.
- Binding a route with only `{ providerId, modelId }` keeps its existing fallback and params; an explicit `fallbackProviderId: null` removes the fallback.
- **Hub panel** (`ProviderHubPresenter` + `handlers/provider-hub.*.handlers.ts`, in the `config-bot` thread): three `StringSelectMenu` (provider, capability, model, catalog paginated by 25) and guarded buttons/modal. Owner or Administrator only (`GuildAdminPolicy`).
- **Tools**: `provider.list/upsert/delete/test/models`, `capability.bind/list`, `providers.panel`. Keys typed in natural language stay visible in the Discord message: the system prompt steers key entry to the hub modal.
- Media: `generateImage` (module `imagelab`) runs the `image.generate` route of the guild through `runCapability`, whatever the protocol (`{ images }` for OpenAI-compatible, `{ urls }` for a polled kie.ai task), downloads through `safeFetch` and delivers ONE attachment. There is ONE `generateImage`: the old direct kie.ai image generator is gone. Music reads its credentials from the `music.generate` route (`credentialsFor`).
- **Model kinds** (`provider-model.kinds.ts`): what a model can do, read from the `/models` metadata (output modalities, capability flags) else from its id. `bindRoute` refuses a catalog model that declares it does not serve the capability and names those that do; an id that is not in the catalog passes. The hub model menu lists every kind a model serves; a `custom.*` capability lists the whole catalog. The family of a capability (`capabilityKind`, shared) is read from a table for the native ones (`web.search` is `search`: its head `web` used to read as `custom`, which skipped the model check and listed the whole catalog), else from the head of its name, else `custom`.

### Other pillars

- **Encrypted integrations** (`modules/integrations/`): `IntegrationService` (instance, rows `IntegrationConfig`) + `GuildIntegrationService` (per guild overrides, table `GuildIntegration`) + AES-256-GCM (`shared/crypto/secret-box.ts`). The instance configuration (LLM/PixelLab/kie), connectable from Discord by owner OR admin; the database has the absolute priority over the environment. Saving the LLM key goes through `LlmService.applyConfig` (connection check + in-memory reload + encrypted persistence + realignment of the guild copies). `IntegrationService.upsert` alone only writes the DB. A guild can keep its own key per integration: the guild key wins, a disabled row cuts the integration for that guild only.
- **Providers AI vs integrations**: a provider is a models API routed by capability (`GuildProvider` + `CapabilityRoute`). An integration is a specialized API with its own tools (PixelLab: `image.icon`, `image.emoji`), never a route target. `providers/image-engines.ts` writes the single line the agent arbitrates on (`MOTEURS D'IMAGE de ce serveur`): pixel art, sprites, icons and emojis go to PixelLab, any other render to `generateImage`; with no engine the agent refuses honestly.
- **Guild rules** (`modules/rules/`): free zones, strictMentionElsewhere, confirmDestructiveActions, blockedChannelIds, custom instructions. Read in code by the gate and the registry, injected into the system prompt.
- **Per-guild agent settings** (`modules/guild-config/`): `AgentSettingsService` (thinking mode, config thread) and `ConfigThreadService` (private `config-bot` thread; tools `config.panel`, `server.overview`, `config.thinking`). A request for "the configuration" shows only what is applied on that guild (rules, skills, integrations with their models, thinking mode): never keys, never the blueprint catalog, never the legacy config sections.
- **Thinking** (`modules/assistant/llm-thinking.ts`, decided by `LlmService.planRequest`): STABLE per request. `preferReasoning` is decided once from the guild setting (`adaptive` by default: on for action requests only) and never changes during the loop; it selects the `chat.reasoning` route when the guild has one, `chat.default` otherwise. The `reasoning_effort` value is decided against the provider that will run the request, and sent only to endpoints that accept it (DeepSeek, Anthropic).
- **Request intent** (`request-intent.ts`, lexicon in `request-intent.lexicon.ts`): an action needs an explicit signal, else the request is plain conversation. Three signals: a matched recipe, an action verb (mutate, create, configure, schedule), or a mutating tool written in the request. A tool merely routed by keyword overlap is NOT a signal: with 171 tools, the old rule sent 109 of 113 turns of one night to `chat.reasoning`. A question (`comment`, `quel`, `est-ce que`...) ignores the verbs and recipes that follow its marker, unless a polite capability preface opens the request (`est-ce que tu peux`, `pourrais-tu`, `peux-tu`). Verbs match whole words with Unicode boundaries (the native word boundary is ASCII and never matches before an accent: `éditer`, `épingler`). The bare verb `mettre` is not in the lexicon, only `mettre à jour` and `mettre en place`; verbs that double as a noun (`active`, `archive`, `poste`, `programme`, `règle`) count only at the start of the request or after a subject. A tool named in the request is a mutating tool when `TOOL_EFFECTS` says `write`: the same table as the approval gate. The regex it replaces had forgotten 29 read tools, whose name written in a request counted as an action.
- **Message delivery** (`shared/utils/message-split.ts`, `shared/utils/mass-mentions.ts`): the final answer is cut by `splitDiscordMessage` into pieces of at most 2 000 UTF-16 units, never inside an emoji, a link, a mention or a code block (paragraph, then line, then space). Every send of text written by the model (final answer, `sendMessage`, `webhook.post`, pipeline steps, jobs, component replies, `ctx.reply`) goes through `massMentionPolicy.guard`: `@everyone` and `@here` are neutralised unless the requester is the owner or an Administrator. The system prompt carries the rule `SYNTAXE DISCORD`. A role mention written in the text is not covered.
- **Outgoing requests** (`shared/utils/safe-fetch.ts`): every request to the web goes through `safeFetch`, `safeFetchText`, `safeFetchBytes` or `safeFetchJson`. Https only; the host is refused on its form and on what it resolves to (loopback, private, link-local, reserved), at EVERY hop: redirects are followed by hand (10 max), because a public address redirecting to the internal network passed the guard when the runtime followed them. Towards another origin the `Authorization`, `Cookie` and `Proxy-Authorization` headers do not follow. The bounded readers cap the body (5 Mo by default, on the declared length, then on the bytes received). `timeoutMs: null` leaves the deadline to the caller's signal (the LLM stream). No raw `fetch` outside `safeFetch`.
- **Feeds** (`webtools/xml-guard.ts`): `readRssFeed` and `getNews` read in https, refuse any `DOCTYPE` or `ENTITY` declaration BEFORE parsing, and parse with `processEntities: false` (the library's default reads the DOCTYPE and expands its entities). `decodeXmlText` decodes the five predefined entities and numeric references only, outside CDATA sections.
- **Observability**: `requestId` is set on the conversation's `ToolRunContext`, so the registry's audit rows and `tool.run` lines carry it, and so does each LLM row of `logs/llm.jsonl` (the conclusion turn at the step ceiling is logged too). `llm.usage` carries `turns` (every LLM call of the request). A thrown handler, a failed loop and a failed request log `describeError` (class, message, chain of causes) and `stackExcerpt` (6 frames, single line, project paths relative, dependency paths shortened): `error-stack.ts`. Every LLM line of `logs/llm.jsonl` carries `guildId` too, and the call that writes the plan summary has its own line (cause `plan.summary`).
- **The model is told the same** (`system-prompt.builder.ts`, rule `SILENCE EN COULISSE`): act without narrating, deliver the result in the final answer. The text of a turn that carries tool calls is never the answer and is thrown away (`AgentLoop`).
- **Decision journal** (`assistant/agent-decision.recorder.ts`, `agent-decision.journal.ts`, table `agent_decisions`): one row per request the model handles, on Discord and from the web: intent (`action` / `conversation`) and the signal that decided it, whether it reasoned and its effort, turns, tools, failures, outcome (`replied`, `silent`, `cached`, `failed`, `ceiling`, `quota`), the steps received from `ctx.progress` and the summary of each tool result (200 characters each, 60 steps, then a count), tokens and duration. Never the requester's message, never the input of a tool. A failed write never breaks a request. Rows older than 14 days are purged at boot, then at most once an hour after a write.
- **Skills** (`modules/agent/`): 135 `SkillBlueprint` recipes in 10 domain files (tool references verified at compile time through `RegisteredToolName`), `search_skills`, learning loop (`SkillPatternDetector`).
- **Memory** (`modules/memory/`): consolidated member/guild profiles (LLM curator with budget and anti-wipe guards), full opt-out, guild history ingestion at GuildCreate.
- **Memory corrections** (`memory/memory-correction.*.ts`, table `memory_corrections`, tool `memory.correct`, classified `write`): a correction replaces a fact kept about a member or the guild, and holds in three places. The prompt gets the correction as is, and it wins. The journal entries that carry the old fact are marked `supersededAt`, never deleted, and are no longer read. The curator receives the active corrections at every merge, and a code check (`enforceCorrections`: 70 % of the stems of the old fact, 2 at least) rewrites the corrected form if the merge dropped it. A correction that replaces an older one marks that one superseded: only the last link of a chain is active (20 active at most). A fact is 3 to 300 characters (500 for the new one), a correction that repeats what it claims to correct is refused, and nothing is kept about a member who asked to be forgotten.
- **Graceful shutdown** (`health/shutdown.service.ts`, in the `@Global` `HealthModule`, last of `imports`; accessor in `health/shutdown.runtime.ts`): on SIGTERM or SIGINT the framework runs the shutdown hooks, disconnects the bot and exits. `ShutdownService.onShutdown` drains first, bounded by `SHUTDOWN_GRACE_MS`: the probe answers 503 (`draining: true`), the SSE streams of the dashboard are closed, the queue takes no new request (a new one is refused with a notice) and waits for the ones being processed (the waiting jobs stay with BullMQ for the next boot), and the tracked work (a conversation from the web) finishes. The database closes AFTER, because `PrismaService.onShutdown` awaits `awaitShutdownDrained()`. Past the grace the shutdown goes on and says what was abandoned.
- **Records** (`modules/records/`): typed store over Prisma. 7 native collections (reminders, suggestions, quotes, faq, counters, notes, component_votes) plus any well-formed dynamic collection a recipe needs (`CollectionQuotaPolicy`: 50 collections and 10 000 records per guild, bounded JSON document).

### Web dashboard and HTTP API (`apps/dashboard`, `modules/api/`)

The dashboard is a SPA over the bot's own HTTP server. A write from the web goes through the same service as the tool: one implementation, two doors.

- **Contract first** (`packages/shared/src/schemas/dashboard-*.ts`, one file per group: common, providers, integrations, webhooks, rules, events). The bot validates with these schemas, the dashboard validates what it reads (`lib/api.ts`: `api.get/post/put/patch/delete`, `ApiError` with `details`, a redirect to the login on 401). A response is an envelope that names its resource: `{ provider }`, `{ routes, followedBy }`, `{ integration }`, `{ webhook }`, `{ rules }`, `{ settings }`, and a removal answers `200 { removed: true }` (never 204, which carries no JSON body).
- **Routes** (`modules/api/*.controller.ts`, one per group, all under `/api/v1/guilds/:guildId/`): `providers` (list, create, patch, delete, test, models: list, add, remove), `capabilities` (list, bind `PUT`, unbind `DELETE`), `integrations` (list, upsert `PUT`, test, delete), `webhooks` (list, create, patch, delete, ping), `rules`, `agent-settings`, `usage` (24 h, 7 d, 30 d), `events` (SSE), and `GuildsController` (guild, config, modules, channels, roles, audit, memories, stats, `agent/chat`, `agent/requests/:requestId`). `AuthController` mounts better-auth on `/api/auth/*`, `MetaController` the session and the module catalog, `LegalController` the terms and the privacy page, `HealthController` `/healthz`.
- **Guards**: every route carrying `:guildId` is declared `@HttpGuards(SessionGuard, GuildAccessGuard)`. `GuildAccessGuard` re-reads Discord on EVERY request and caches nothing: the member must still be in the guild and pass `GuildManagerPolicy` (Manage Guild, Administrator or owner). A role removed closes the access at the next call. The guild list needs the session only. `app.module.spec.ts` holds these invariants: a guild route without both guards, `GuildAccessGuard` without the session before it, or `PanelController` anywhere but last fails the suite.
- **`PanelController` is LAST** in `controllers`: its `GET /*` catches everything the API, the login and the probe do not serve.
- **Policy** (`ApiPolicyMiddleware`, global, before any route): `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow` on `/api/*`; **every non-GET of `/api/v1` must come from a trusted origin** (`Origin` when present, even `null`, else `Referer`; 403 otherwise). The session travels in a cookie: without that check a third-party page drives the browser of a signed-in member. `DASHBOARD_ORIGIN` holds several origins, comma separated; the first carries the OAuth callback.
- **CSP**: `API_CSP` (`default-src 'none'`) on every response, `PAGE_CSP` on the only HTML pages of the bot (compiled panel, legal pages), never under `/api/`. The CSP of the framework is disabled (`httpSecurity`, `modules/api/http-security.ts`) because the framework sets its own after each handler on every response.
- **No secret leaves the bot**: a view carries `{ hasApiKey, keyHint }` (`shared/crypto/key-hint.ts`: four dots and the last four characters, the dots alone under 8 characters). A create or an update whose key is empty or absent keeps the stored secret, an explicit `null` removes it. A webhook view names its secret headers, never their values.
- **Outgoing addresses**: a provider base URL and a connector URL pass `assertProviderUrl` and the webhook input guard (https, public host, checked on what it resolves to): no loopback, private, link-local or reserved address, and no credentials in a connector URL (they go into encrypted secret headers).
- **SSE** (`EventsController` + `DashboardEventsService`, hooked on `AuditService`): `GET /api/v1/guilds/:guildId/events`, guarded like the rest, one stream per guild, subscribed before the open write. An event is `{ type }` and nothing else (`DASHBOARD_EVENT_TYPES` in shared: provider, capability, integration, webhook, rules). Its only job is to invalidate the queries of the displayed guild, which then re-reads what it has the right to read. A `ping` every 25 s keeps the stream open behind a proxy.
- **Live steps of the web channel** (`RequestProgressService`, assistant module, in memory: 200 entries, a finished request disappears after 10 minutes): the panel sends the `requestId` it chose (`web-<uuid>`), the agent records its steps there, the panel polls `agent/requests/:requestId`. A request is read from its own guild only.
- **Usage** (`modules/usage/`): each model call is counted in `llm_usage_rows` with the values of its `logs/llm.jsonl` line (`UsageLogService`, written by the agent loop and the plan summary), `UsageReaderService` aggregates the three windows.
- **Outgoing HTTP connectors** (`modules/webhooks/`, table `webhook_endpoints`, 20 per guild): an endpoint of an external service that a trigger, a recipe or the model calls. The tool `webhook.call` gives a slug and a short JSON payload, never the address nor the headers, and is classified `write`. `WebhookExecutor` serves the test (`ping`) and the call with the same path: `webhook-request.builder.ts` (template, extraction path), `webhook-http.ts` (through `safeFetch`, redirects followed by hand and towards the same origin only: the secrets of a connector never leave the origin the staff configured), then the last status is recorded. A failure is an explicit `ok: false` with its reason.
- **Production**: with `DASHBOARD_DIST_DIR` set, `PanelController` serves the compiled panel on the bot's own origin: an existing file as is (`/assets/` immutable for a year, every other path `index.html` with `Cache-Control: no-cache`). A path that climbs out of the folder falls back on the page of the router or 404, never on a file outside. Without the setting, unknown paths get the JSON 404. A relative `DASHBOARD_DIST_DIR` is resolved from the working directory, from the repo root and from `apps/bot` (`panel-dist.ts`), so the same value works from a shell at the root or in `apps/bot`.
- **Auth**: `AuthController` answers 503 with the cause when Discord OAuth is not configured (`BETTER_AUTH_SECRET`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`). The login asks `identify` only, the OAuth tokens are dropped when the account is created or updated (`scrubOAuthTokens`), the session cookie is `Secure` on an https origin, `trustedOrigins` accepts several origins (`auth-origins.ts`). `/healthz` is the only route behind `ProbeKeyGuard` (`HTTP_API_KEY`): the dashboard API authenticates by session, never by a global key. It answers `{ ok, uptimeSec, gatewayReady, db, queue, driver, draining }`, 200 or 503 as soon as a component is missing or the drain has begun, and the `HEALTHCHECK` of the image reads it (the key comes from the environment of the container).
- **Dashboard** (`apps/dashboard/src`): `ds/` (the primitives: Button, Input, Select, Tabs, Sheet, ConfirmDialog, DataTable, Badge, Kpi, Feed, Process, CardList, Typed, Boot), `shell/` (top bar, mobile bottom menu, guild context, search palette, More panel, page frame), `lib/` (`api.ts`, `events.ts`, `progress.ts`, `queries.ts`, `format.ts`, `i18n/`: FR and EN, the keys typed from the French file), `pages/` (`login`, `guilds`, `guild/*`: home, providers, integrations, journal, rules, modules, config, memories, system, agent). Theme in `styles/` (`tokens.css`: Tailwind 4 `@theme`, `motion.css`, `theme.css`: notched frames, pixel labels). A date or a duration is never formatted by hand (`lib/format.ts`), a string never written in a component (i18n), a secret never held by the page (`SecretInput` shows nothing).

## Gotchas

### Spraxium runtime

- **The framework never instantiates module classes.** Only `providers`, `listeners` and `handlers` are instantiated and lifecycle-registered. A constructor, `onBoot`, `onReady` or `onShutdown` inside a `@Module` class NEVER runs. Put runtime bindings in a provider's `onBoot`. Three modules carried dead code this way, including the wiring of the destructive-action confirmation, which therefore never fired from day one. `arch-audit` now rejects the pattern (`LIFECYCLE_ON_MODULE`).
- **Interaction handlers need their decorators.** A handler class listed in `handlers: [...]` but without `@ButtonHandler` / `@ModalHandler` / `@StringSelectHandler` (and a matching `@Button` / `@ModalComponent` / select component class) receives nothing from the dispatcher. The dispatcher calls the method named `handle`, with parameters injected by `@Ctx`, `@ButtonParams`, and similar decorators.
- **VALUE imports for injected classes.** `import type` strips the class from `design:paramtypes` → the token becomes `Object` → ModuleLoader fails at boot. Recurred 4+ times (Client, IntegrationService).
- **No default value on a constructor parameter of a DI class.** Same symptom (token `Object`). Instantiate pure helpers such as presenters as class fields instead.
- **`@Global` for cross-module services** - a non-global shared module only exports into the FIRST importer's container.
- A module cannot import another module that loads earlier in `AppModule` to reach its services (temporal dead zone at boot). Use a runtime accessor bound by the owning provider.
- **A provider of `AppModule` is injected by `AppModule` alone, and the HTTP server builds every controller in the ROOT container.** The root module gets a CHILD container of the root one, and its providers are registered after its imports are loaded: no other module can resolve them. The server then builds each controller and each guard against the root container, and refuses nothing: a parameter missing there arrives `undefined`. On 2026-11-25, a CI-green build failed twice on one service declared in the root module: the bot refused to boot (« cannot resolve dependency for WebAgentService »), and once that was lifted its probe answered 500 (« reading 'isDraining' »), while every spec mounted the service by hand. A service that another module or a controller needs lives in a `@Global` module that exports it (`health.module.ts` for `ShutdownService`, loaded AFTER the assistant module whose queue it injects). What only the root module reaches goes through a runtime accessor instead (`shutdown.runtime.ts`).
- **`app.module.scopes.spec.ts` replays both walks** (`ModuleLoader.loadModule`: root container, child containers, provider ordering, exports into the parent or the root, a module loaded once; then the controllers and their guards against the root container) and names the provider, the parameter and the token of anything that cannot be resolved. It replaces neither a boot nor the probe: after a change to a constructor or to a module declaration, START the bot and read `/healthz`.
- Decorator-critical tsconfig flags: `experimentalDecorators`, `emitDecoratorMetadata`, **`useDefineForClassFields: false`** - do not modernize.
- Boot hooks use `SpraxiumOnBoot` (not `OnModuleInit`), and only on providers, listeners and handlers.
- **The framework runs every `onShutdown` in parallel** (`Promise.allSettled`, `ModuleLoader.runShutdownHooks`), then destroys the client and exits. Nothing orders one hook after another: a hook that closes a resource used by work still in flight waits for the drain through `awaitShutdownDrained()` (`PrismaService` does, or the queue would drain on a closed database).
- Handler not firing? Check in order: decorator metadata → class listed in `handlers` → module reachable from `AppModule` → gateway intents → custom id.

### HTTP API and web dashboard

- **A unit spec of a controller sees nothing of the framework's middleware.** The harness mounts one controller on a bare Hono. The panel pages were served under the CSP of the framework (`default-src 'none'`: no script, no style, no font) while every spec was green; found by reading the headers on the running bot (2026-11-25). After any change to a response header, read it on the running bot.
- **The framework owns its CSP**: `SecurityHeadersMiddleware` sets `Content-Security-Policy` after the handler, on every response, whatever the handler set. Its only setting is one string for all responses, or `false`. It is `false` in `httpSecurity` and `ApiPolicyMiddleware` decides per response (`API_CSP`, `PAGE_CSP` on an HTML page outside `/api/`); `app.module.spec.ts` holds the two together.
- A handler that returns a `Response` built by hand does not receive the headers prepared by `ctx.header()` before it, and a header set after an early return is on nothing. A policy header is therefore set twice: before `next()` (errors included) and on `ctx.res` after it. Write it before any `return`.
- `config/http.config.ts` is outside `rootDir` (`src`): a spec cannot import it (TS6059). What the code fixes lives in `src` (`httpSecurity`) and the config passes the environment in.
- The route decorators push into an array: the methods of a controller are registered bottom-up. `declaredRoutes` lists the last method first; keep `PanelController` last regardless.
- The HTTP server builds the controllers and their guards in the ROOT container only (`deps.get(type) ?? fallback.get(type)`, silently `undefined` when missing). A service a controller injects must be exported by a `@Global` module, and every controller is also a provider of `AppModule`.
- **`import type` on an injected class emits the token `Object`**. Found twice in the first draft of the API (the events stream, the events service), by the token check of `app.module.spec.ts`, which walks the whole module graph: any constructor dependency of any provider that is `undefined` or `Object` fails the suite.
- Hono is strict about the trailing slash: `/api/v1/guilds` and `/api/v1/guilds/` are two routes. A list that sits at the root of its prefix declares both (`@HttpGet('')` and `@HttpGet('/')`), with the same guards.
- Hono's `streamSSE` forces `Cache-Control: no-cache`. `EventsController` builds its response on `SSEStreamingApi` by hand, subscribes BEFORE awaiting the open write, and its spec keeps a single read in flight and settles through a real `setTimeout` (`vi.waitFor` under fake timers never sees the stream).
- A connector redirect towards another origin is not followed: followed by the runtime, it would carry the secret headers to a third party.
- **Controller specs**: `apiHarness(deps).serve(controller)`, `request(app, method, path, body)` and `declaredRoutes(controller, guards)` in `controller.test-support.ts`. The guards are mocked with `vi.mock` (the session guard sets `session`, the guild guard sets `guildAccess` and throws `ForbiddenError`); a mock that returns a promise must be async.
- **Stage a new spec before trusting `check:tools`**: the scanner reads `git ls-files`, so an untracked file is invisible to it, and CI reads the committed tree. Nine fake tools (`Test`, `X`, `WebhookEndpointError`...) surfaced only at the first full `verify` of the dashboard lot. `const NAME = 'name'` and a computed key keep a literal out of the registry.
- **Dashboard specs** run in jsdom (`vitest.config.ts`, `src/test/setup.ts` initializes i18n, `vi.hoisted` sets the locale in localStorage before that). `renderWithProviders` mounts a page in the same providers as the app, `stubRoutes` replaces `fetch` with a table (a route missing from the table fails the test). There is no jest-dom: assert with plain `expect`, and prefer `getAllByText` (a title is rendered twice: once animated, once for screen readers). Under `pnpm test` the workspaces run in parallel: a page rendered under jsdom takes several seconds then (one second alone), so a wait lasts up to 15 s and a test up to 30 s (`asyncUtilTimeout` in the setup, `testTimeout` in the config). A spec that fails only in that run, and passes alone, did not fail on what it asserts.
- **Tailwind 4**: in `@theme`, the resets (`--color-*: initial`, fonts, shadows) come BEFORE the custom tokens, or they wipe them (the palette disappeared, found by grepping the built CSS). The custom `text-label` / `text-badge` / `text-desc` utilities are declared to tailwind-merge as font families (`lib/utils.ts`), else `cn` keeps only one of two `text-` classes.
- **A render prop can run twice** (StrictMode renders a child twice with the same props): never fill an array created in the parent during the render of a child. The configuration page showed each of its tabs twice.
- **A modal closes through `useModalDialog().close()`**, never by waiting for the `close` event of `<dialog>`. The embedded browser of the harness never fires it: the opener button was dead after the first closing. Button, backdrop and Escape all go through the same path (`cancel` is always prevented).
- **Visual checks** run against a fixture API, never against the owner's server. In the embedded browser: a synthetic mouse click does not reach React (call `.click()` through `evaluate`), `tab.playwright.press` does not exist (dispatch a `KeyboardEvent`), `dialog.close()` fires no `close` event, and screenshots time out at random: audit by measuring in the page (overflow, truncated text, targets under 44 px) at 1440 px and at 390 px.

### Data and LLM

- **Data access** (`modules/database/`): ONE factory opens the base, `createDatabaseClient(url)` (`database-client.ts`), for `PrismaService` (DI graph), better-auth (`auth.instance.ts`, outside that graph) and the `.mjs` operational scripts, which import the TypeScript factory directly (plain Node erases types: keep those files to erasable syntax, and keep the `.ts` extensions on their relative imports). The client is GENERATED by `prisma generate` into `apps/bot/generated/prisma` (gitignored, rebuilt by `postinstall` and at the start of `dev`, `build`, `typecheck`, `test`): import it by relative path, never from `@prisma/client`, which exports nothing of it under Prisma 7. `prisma.config.ts` is the CLI's only source for the database address.
- **SQLite date format is pinned: `unixepoch-ms`.** The driver adapter is `@prisma/adapter-libsql`, created with `timestampFormat: 'unixepoch-ms'` (the one place: `database-client.ts`). By default Prisma 7 writes dates as ISO text, and a database written by Prisma 6 keeps integer epoch milliseconds: every date filter would then be wrong without one error (`createdAt >= yesterday` returns nothing, `createdAt < 2100` returns everything). Seen on a copy of the real database on 2026-11-25. So the rule stays: `strftime('%Y-%m-%d', "createdAt")` returns NULL, write `"createdAt" / 1000, 'unixepoch'`. `MIN`, `COUNT` and `SUM` now come back as numbers (BigInt under Prisma 6): keep `Number()` around them, and never let a BigInt reach a tool result's `data` (serialize with `stringifySafe` from `shared/utils/object.ts`).
- **A relative SQLite address resolves from `apps/bot`** (`database-url.ts`): `file:./data/bot.db` is the project database, for the CLI (the folder of `prisma.config.ts`) and for the client (the folder the bot is started from). Under Prisma 6 the address resolved from the schema folder, so the old default `file:../data/bot.db` now points to `apps/data/bot.db`, another file. `PrismaService.onBoot` refuses to start on a SQLite file that does not exist and names it: a base is never created empty in silence. The `.mjs` scripts have no such guard: they carry the same default.
- **The SQLite library of the adapter keeps the time zone it was loaded with**, and ignores later changes of `TZ`, while Node follows `process.env.TZ` (and, on Node 27, does not come back when the variable is removed). Never change `TZ` at runtime: the day axis of `usage-reader.service.ts` needs both to agree. A spec that changes `TZ` restores the machine zone before comparing local days (`usage-reader.service.spec.ts`).
- **After `$disconnect()`, libsql keeps the SQLite file taken for a while under Windows** (from 200 ms to more than 20 s after a raw write). The data is written (checked: a process that exits right after the disconnect loses nothing). A spec that deletes its disposable database retries for two seconds, then gives up.
- `reasoning_effort` and other optional provider fields are rejected with a 400 by several OpenAI-compatible endpoints: omit them unless configured and compatible.
- `packages/shared` must be built (`pnpm --filter @10cordes/shared build`) before bot typecheck/dev - the bot imports its `dist/`.
- **`user_id` in the chat body goes to DeepSeek only** (`buildChatRequestBody`, keyed on the host). It is not an OpenAI field: a strict endpoint rejects the whole request with a 400.
- Host rules are exact: `deepseek.com` and its subdomains (`isDeepSeekHost` in `shared/llm/chat-utils.ts`), never a look-alike domain.
- Every provider failure is typed. `ProviderError.kind` (`provider.types.ts`) comes from adapters, `ProviderHttpError`/`ProviderUnavailableError`/`ProviderTimeoutError`/`ProviderAuthError`/`QuotaExhaustedError` (`llm.errors.ts`) from the protocols the client serves itself. The fallback decision reads both through `isFallbackWorthy`; a new error class must be classified there.
- The LLM usage log (`logs/llm.jsonl`) carries `provider`, `model` and `fallback`: the model that actually answered, read from `ChatCompletionResult.served`.
- **French apostrophes in strings: `\u0027`, never `\u0029`.** `\u0029` is a closing parenthesis and compiles without any error, so the text reads « d)un » (153 occurrences swept on 2026-11-23). After writing French text, `grep -rlF '\u0029' --include='*.ts' apps/bot/src packages/shared/src` must return nothing.
- Editing the wording of a blueprint `trigger` makes the seed create a new row and purge the old one. The seed (`skill-blueprint.library.ts`) reactivates a purged library row whose trigger is back in the catalog, unless the staff deleted it (audit trail of the `deleteSkills` tool).
- Zod: nested defaults need **`.prefault({})`**, not `.default({})`. Zod 4 recursive types: declare manual union types.
- Prisma **7.10.1, exact version** for `prisma`, `@prisma/client` and `@prisma/adapter-libsql` (the CLI, the client and its driver adapter must move together). The schema carries no `url` and no `prisma-client-js` generator any more: `datasource db { provider = "sqlite" }` and `provider = "prisma-client"` (TypeScript output, `importFileExtension = "ts"`). SQLite has no Json type → String column + `JSON.parse/stringify` at service level. `pnpm-workspace.yaml` still lists `@prisma/client` under `allowBuilds`: harmless, leave it.
- Migrations on the dev DB are applied by hand, never with a reset: that DB holds encrypted keys and real guild rules. From `apps/bot`: copy `data/bot.db`, then `pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` gives the SQL of the change (the real database against the schema), `pnpm exec prisma db execute --file <migration.sql>` applies it and `pnpm exec prisma migrate resolve --applied <name>` records it. No `--schema` on `db execute` (rejected) and no `DATABASE_URL=` prefix is needed: `prisma.config.ts` reads the address from the environment of the command, then `.env.local`, then `.env`, then the default. To aim at a copy, set `DATABASE_URL` in the command. `prisma generate` is safe to run while the bot runs (it rewrites `generated/prisma`, already loaded in memory).
- kie.ai `recordInfo` gives the state of a task in `state` (`waiting`, then `success`) and in `successFlag`, and a failure in `failCode` / `failMsg`. There is NO `status` field: an adapter that read it waited the whole delay on an image ready in 8 s (seen live on 2026-11-24, after a spec written from a guessed fixture). `isDone` (`kie-unified.jobs.ts`) also delivers a task with an unknown state that already carries files. A fixture that stands for a real provider response must come from an observed one.

### Testing and rigs

- **A rig proves nothing by checking that a tool was called.** Check `ok: true` in the audit row `assistant.tool.<name>` (its metadata carries `ok` and `summary`), and keep failed tool calls visible in the scenario note. Name-only checks reported PASS on failing tools for a whole afternoon.
- A rig must assert something created DURING the scenario, not a row left over from an earlier run.
- **Never rebuild or restart the bot while a rig is running**, and boot the bot after any change to a DI constructor before trusting a rig.
- Component clicks and modal submits cannot be simulated from a rig (a real Discord interaction is required). Cover them with unit tests on the handler (metadata, policy guard, effect) and say plainly that the real click is unverified.
- `sync-tool-names.mjs` scans `name: '...'` literals in tracked sources: a fake tool in a spec file would enter `REGISTERED_TOOL_NAMES`. Use a constant for the name. `pnpm check:tools` (in `verify` and CI) fails when `registry-names.ts` is stale; a new source file must be known to git (`git add -N`) to be scanned. A `name: 'Some text'` object key in a spec is scanned too, even when it is not a tool (a channel name given as a tool parameter entered the registry on 2026-11-24). Then give the tool its line in `TOOL_EFFECTS`: the type and `tool-effects.spec.ts` both fail until every registered name is classified, and a tool flagged `destructive` must be `write`.
- A spec that stubs `fetch` under fake timers must also mock `node:dns/promises` (`vi.hoisted` + `vi.mock`, as in `safe-fetch.spec.ts`): the outgoing request guard resolves the host before every call, and a real lookup never completes under fake timers, so the test hangs. To read the JSONL log from a spec: `setFileLog({ event, llm })` and `setFileLog(null)` in `afterEach`.
- `fast-xml-parser` with its default options reads the DOCTYPE, expands the entities it declares, and turns a text node into a number or a boolean (`007` becomes 7). A document that comes from the web is parsed with `SAFE_XML_OPTIONS` only.
- A modal holds at most 5 components and a 45-character title, and Discord rejects the whole modal beyond that (the click stays silent). Declare `required: false` on optional inputs, Discord requires them otherwise. Every modal passes `assertModalFits` (`shared/ui/modal-limits.ts`) before `showModal`, and its spec counts the components of the built modal.
- Rigs: `e2e-gate.mjs` (gate: intruder, unaddressed, mention, reply, other bot, and `gate.silence`: during a request that runs a tool, the channel is sampled every 2 s and the bot must write nothing but the final answer), `e2e-full-suite.mjs` (its `rule.confirm` turns the rule on by the bot, then checks that a deletion AND a rename are held, that a read passes, that one plan was posted per request with the title of the rule and the model's summary on the first panel, and that nothing ran), `e2e-surface.mjs`, `e2e-providers.mjs` (multi-provider engine: migration, inventory, connection test, model change, automatic fallback, hub panel). `E2E_ONLY=name` runs one scenario. The typing indicator is not a message: REST cannot see it, only the unit tests cover it.
- While the rule « Confirmer les actions (hors lecture) » is on, a rig cannot ask the bot to turn it off: `rules.set` would itself wait for a click. The cleanup writes the database and lets the rules cache expire (60 s).
- A provider that must fail on purpose in a rig: base URL `https://192.0.2.1/v1` (documentation address, never reachable). Local mock servers are refused by design by the outbound request guard.
- Every scenario in a rig must restore what it changed (rule toggles, probe channels, test surfaces).
- Every conversational scenario of `e2e-full-suite.mjs` reports its LLM turns (rows of `logs/llm.jsonl` between the `tools.selected` and `assistant.reply` audits) and the capability that served them. `tickets.surface` passes only under 5 turns, without the step ceiling, and deletes the surface it created.
- `pnpm lint` is two passes. The TypeScript pass (`eslint.ts.config.mjs`) enables four rules only (`no-floating-promises`, `await-thenable`, `no-unused-vars`, `no-explicit-any`): a violation is fixed, never disabled. The `@bluzzi` TypeScript block stays off because `typescript` is not installed at the root: `pnpm exec eslint --print-config apps/bot/src/main.ts | grep -c "@typescript-eslint"` must print 0. The pass types through the tsconfig files, so `lint` builds `@10cordes/shared` first. Files outside any tsconfig `include` (the bot's `config/*.ts` and `spraxium.config.ts`, `packages/shared/tests/*.spec.ts`) are typed through the default project, which typescript-eslint caps: `maximumDefaultProjectFileMatchCount_THIS_WILL_SLOW_DOWN_LINTING` in `eslint.ts.config.mjs` must stay above their number (24 for 15 files). A spec added to `packages/shared/tests/` counts there; so does any new config file outside a tsconfig `include`, which must be added to `allowDefaultProject` (its list holds `packages/shared/vitest.config.ts`): otherwise the lint fails on that file with "not found by the project service".
- **Coverage is a floor on `packages/shared`** (`packages/shared/vitest.config.ts`, `@vitest/coverage-v8`): 80 % of lines, functions, branches and statements, or `pnpm test` fails. Barrels and type-only files are out of the count (`src/index.ts`, the tool registry, `schemas/dashboard.ts`, `schemas/surface.ts`, `skills/blueprint.ts`, `types/module-descriptor.ts`): a new one goes into that list, never a lowered threshold. The shared package is the contract the bot validates with and the dashboard reads with: a regression there breaks both without a sound.
- **Read the source before writing an expected value.** Six expectations of the first shared specs were guesses and failed on themselves: a trailing dash is accepted in a binding key, `providerId` is not trimmed, an instruction of 3 characters is accepted. A wrong expectation that passes after "fixing the code" is how a defect gets baked in. One of those specs did find a real defect (`web.search` read as `custom`): that is what they are for.
- **gitleaks is always run with `--redact`.** Never print a report or a log that is not redacted: the local scan goes through the official image (`ghcr.io/gitleaks/gitleaks:8.30.1`), with the report written outside the repository. A scan that finds nothing proves only that no known pattern was matched, never that the history holds no secret.

### Environment and tooling

- `dev.exclude` must keep `.spraxium/**` and `dist/**` (watcher restart loops otherwise).
- Env files: `.env.local` > `.env` > `process.env`; no variable interpolation. `process.env` access outside config files is an arch-audit violation.
- Artifacts: `.spraxium/` build, `data/` SQLite DB, `logs/` JSONL, `.mimosa/` hook state - all gitignored.
- In Git Bash on Windows, a grep pattern that starts with `/` (such as `/setup`) is rewritten into a Windows path and silently matches nothing. Use a character class (`[/]setup`) or `grep -F`.
- The bot runs from `.spraxium/dist`: rebuild and restart after any fix, and stop every bot process before dropping a database table (a stale process kept querying a dropped table and spammed the framework's default error).
- Starting the bot from a shell: `pnpm start` in `apps/bot`. Find bot processes with a PowerShell CIM filter on `node.exe` and a command line matching `spraxium|10cordes`.
- **Docker**: the image's `CMD` ends with `exec node`, so node, not the shell, receives SIGTERM; the compose file adds `init: true` and `stop_grace_period: 30s`, which must stay above `SHUTDOWN_GRACE_MS` (20 s by default): a stop that reaches the end of the grace kills the process.
- **Never print a resolved configuration.** `docker compose config`, a parsed `.env`, an environment dump: a black list of variable names always misses one (a legacy key was printed in a tool output on 2026-11-25). Use `--quiet`, `--services`, or a script that prints key NAMES only; to know whether a variable is set, count the matches of `^\s*NAME\s*=\s*\S+`, never print the line.
